Q1. STRUCTURAL QUALITY SCORE
--------------------------------------------------------------------------------
VERDICT: Formula correct, but one cap is missing. Professionalism confirmed to
         have zero weight.

Source: test/ScoringEngine.cs:151-186

    r.Norm_Complexity = Clamp01(1.0 - (s.CyclomaticComplexity / cfg.MaxAcceptableComplexity)); // 15
    r.Norm_Nesting    = Clamp01(1.0 - (s.MaxNestingDepth      / cfg.MaxAcceptableNesting));    // 5
    r.Norm_Style      = Clamp01(1.0 - (s.NamingViolations     / cfg.MaxAcceptableNaming));     // 10

    double qNum = cfg.W_Complexity * r.Norm_Complexity
                + cfg.W_Nesting    * r.Norm_Nesting
                + cfg.W_Style      * r.Norm_Style;
    double qDen = cfg.W_Complexity + cfg.W_Nesting + cfg.W_Style;   // = 3
    r.QualityScore = (qDen > 0 ? qNum / qDen : 0) * 100.0;

The code computes an unweighted mean of three inverse-normalised terms, not a
90-point penalty budget. Expanding:

    100/3 * [(1 - C/15) + (1 - N/5) + (1 - V/10)]
      = 100 - 2.22*C - 6.67*N - 3.33*V

The manuscript's (100/90)*(90 - 2C - 6N - 3V) expands identically.
THE FORMULA IS ALGEBRAICALLY EQUIVALENT - KEEP IT.

THE ERROR IS THE NAMING TERM. Clamp01 is applied to each term independently, so
naming violations saturate at MaxAcceptableNaming = 10, exactly as complexity
saturates at 15 and nesting at 5. The manuscript writes 3*NamingViolations
uncapped, which diverges for any solution with V > 10 and goes negative past
V = 30.

CORRECTED FORM:

    Quality = (100/90) * ( 90 - 2*min(C,15) - 6*min(N,5) - 3*min(V,10) )

CAPS ARE EXPLICIT NAMED CONSTANTS, not artifacts - test/ScoringEngine.cs:44-46

    public double MaxAcceptableComplexity { get; init; } = 15.0;  // McCabe guidance
    public double MaxAcceptableNesting    { get; init; } = 5.0;
    public double MaxAcceptableNaming     { get; init; } = 10.0;

PROFESSIONALISM CONTRIBUTES NOTHING - the suspicion is confirmed.
ProfessionalismScore is not a field of ScoreInputs at all. Its two constituent
booleans ARE passed in (test/Program.cs:86-87 -> ScoringEngine.cs:93-94) but
Compute() never reads them. A full-repo trace shows every usage is either an
assignment or Excel output (column 13, ProgramMain.cs:249); no read reaches any
score. The metric is reported but inert.

The same trace shows AllocatedBytes is likewise declared, populated, and never
read (ScoringEngine.cs:98). MEMORY HAS ZERO WEIGHT IN EFFICIENCY, which is
time-only. If the manuscript describes efficiency as covering time and memory,
that needs correcting too.

Q3. COMPOSITE SCORE
--------------------------------------------------------------------------------
VERDICT: Weights and renormalisation both correct - but the provenance is
         misstated.

Source: test/ScoringEngine.cs:191-201

    double w_c = cfg.ExcludeCorrectnessFromQuality ? 0.0 : cfg.W_Correctness;
    double perfWeight = hasBenchmarkData ? cfg.W_Performance : 0.0;
    double num = w_c * r.Norm_Correctness + cfg.W_Complexity * r.Norm_Complexity
               + cfg.W_Nesting * r.Norm_Nesting + cfg.W_Style * r.Norm_Style
               + perfWeight * r.Norm_Performance;
    double den = w_c + cfg.W_Complexity + cfg.W_Nesting + cfg.W_Style + perfWeight;
    r.CompositeScore = (den > 0 ? num / den : 0) * 100.0;

Weights are five EQUAL UNIT WEIGHTS OVER SUB-COMPONENTS (ScoringEngine.cs:51-55,
all = 1.0), not a 0.2/0.2/0.6 triple over axes. With benchmark data den = 5;
since Quality is the mean of three of those five, the 0.2/0.2/0.6 split falls
out arithmetically. Without benchmark data den = 4, giving

    0.25*Correctness + 0.75*Quality

which is identical to the manuscript's /0.8 renormalisation. Both confirmed.

WHY THE DISTINCTION MATTERS FOR REVIEW: the 60% weight on quality is not a
design choice, it is a consequence of quality having three of five
sub-components. Presenting it as a deliberate emphasis invites a challenge the
code cannot support. Describe it as equal weighting of five normalised
sub-scores, and note the induced 3:1 emphasis.

Excluded rows return at ScoringEngine.cs:140-148 before any of this, leaving
CompositeScore = 0.

VERDICT: The code writes BYTES PER OPERATION. The values are not megabytes -

Source: test/ProgramMain.cs:440-448

    static double AllocBytesPerOp(BenchmarkDotNet.Reports.BenchmarkReport report)
    {
        long totalOps = report.AllMeasurements
            .Where(m => m.IterationMode == BenchmarkDotNet.Engines.IterationMode.Workload)
            .Sum(m => m.Operations);
        return totalOps > 0
            ? (double)report.GcStats.GetTotalAllocatedBytes(false) / totalOps
            : 0.0;
    }

  FIELD READ ..... GcStats.GetTotalAllocatedBytes(false) - cumulative allocated
                   bytes, NOT Gen0 collection counts.
  CONVERSION ..... division only. No unit scaling exists anywhere in the repo.
  THE DEFECT ..... the filter constrains IterationMode but NOT IterationStage,
                   so the denominator sums operations across Pilot, Warmup,
                   Actual AND Result stages, while the numerator covers only
                   actual workload iterations. The result is systematically too
                   small by roughly the stage-multiple.

EMPIRICAL CONFIRMATION. The BenchmarkDotNet artifacts under
test/bin/Release/net8.0/BenchmarkDotNet.Artifacts/results/ give ground truth.
For csharp_43 / Llama, BDN's own "Allocated" column reads 8,589,938,640 B while
the pipeline wrote approximately 4.2e7 - a factor of about 204.

The in-code comment at ProgramMain.cs:437-439 claiming the calculation "match[es]
how BenchmarkDotNet's own [MemoryDiagnoser] column is computed" is incorrect on
both the divisor and the excludeAllocationQuantumSideEffects: false flag.

ON THE ZERO VALUES - GENUINELY AMBIGUOUS. Three indistinguishable causes:

  (a) Rows never reached by phase 3. Every row is first written with memory
      hard-coded to 0 (ProgramMain.cs:180, BuildScoredRow(..., 0, 0, cfg)) and
      only overwritten if a benchmark report exists.
  (b) totalOps == 0 -> the 0.0 placeholder in the method above.
  (c) A true zero-allocation measurement. Real and common here; the artifact
      CSVs show Alloc=0.0000 for many stack-only solvers.

The code cannot distinguish these.

RECOMMENDATION: rebuild the column from the 79 artifact CSVs' "Allocated" field,
which is per-operation, correct, and distinguishes empty from zero. That also
recovers the Gen0 column.

Q5. NAMING CHECK - THE REVIEWER IS CORRECT

VERDICT: Signature identifiers ARE counted. The objection must be conceded.

Source: test/CodeEvaluator.cs:292-306, in full

    private void AnalyzeNamingConventions(SyntaxTree tree, CodeQualityReport report, string expectedMethodName)
    {
        var root = tree.GetRoot();
        var method = root.DescendantNodes().OfType<MethodDeclarationSyntax>()
                         .FirstOrDefault(m => m.Identifier.Text == expectedMethodName);
        if (method != null && method.Identifier.Text.Length > 0 && char.IsLower(method.Identifier.Text[0]))
            report.NamingViolations++;

        var identifiers = root.DescendantNodes().OfType<ParameterSyntax>().Select(p => p.Identifier.Text)
            .Concat(root.DescendantNodes().OfType<VariableDeclaratorSyntax>().Select(v => v.Identifier.Text));

        foreach (var name in identifiers)
            if (!string.IsNullOrEmpty(name) && char.IsUpper(name[0]))
                report.NamingViolations++;
    }

  NODES VISITED ............... MethodDeclarationSyntax (one only),
                                ParameterSyntax (all),
                                VariableDeclaratorSyntax (all)
  ENTRY-POINT METHOD EXCLUDED?  NO - it is the ONLY method checked
  ENTRY-POINT PARAMS EXCLUDED?  NO - all parameters in the file are scanned
  IdentifierName .............. not visited
  PropertyDeclarationSyntax ... not visited
  CLASS NAME "Solver" ......... NOT CHECKED (no ClassDeclarationSyntax visit)

RULES: exactly two, both first-character-only.
  - Method: flagged if it starts lowercase.
  - Parameters and variable declarators: flagged if they start uppercase.
  No underscore, full-PascalCase or full-camelCase validation. Both
  "my_variable" and "XMLHttpRequest" pass.

WHY THE OBJECTION HOLDS: parameter names come from the task signature, so they
are prompt-determined and identical across all seven models. They add a constant
offset per task rather than a model signal.

NUANCE ON THE METHOD NAME: expectedMethodName is NOT read from the task spec. It
is re-derived from the model's own code by regex (ProgramMain.cs:131-135, first
public method). It therefore measures the model's emitted name - but since the
prompt supplies the entry point, in practice it echoes the prompt.

TWO FURTHER SCOPE ISSUES TO ADDRESS WHILE RECOMPUTING:
  - VariableDeclaratorSyntax also matches FIELD declarations, so
    "public const int MaxSize" - correct C# - is counted as a violation.
  - Only the entry-point method is name-checked. HELPER METHODS THE MODEL WROTE
    ARE NEVER CHECKED, so the metric is blind to exactly the naming the model
    chose freely.

RECOMPUTATION SHOULD: exclude the entry-point method name and all parameters of
that method; ideally add helper-method names.

Q7. ExtractMethodBodyRobust
--------------------------------------------------------------------------------
VERDICT: The literal/comment-skipping claim is FALSE. The pseudocode asserts
         behaviour the implementation does not have.

Source: test/SolutionWriter.cs:192-220, verbatim

    private string ExtractMethodBodyRobust(string rawCode)
    {
        if (string.IsNullOrEmpty(rawCode)) return "// No test code found";

        var mainMatch = Regex.Match(rawCode, @"Main\s*\(.*?\)");
        if (!mainMatch.Success) return rawCode;

        int startIndex = rawCode.IndexOf('{', mainMatch.Index);
        if (startIndex == -1) return rawCode;

        int openBraces = 0;
        int endIndex = -1;

        for (int i = startIndex; i < rawCode.Length; i++)
        {
            if (rawCode[i] == '{') openBraces++;
            if (rawCode[i] == '}') openBraces--;

            if (openBraces == 0)
            {
                endIndex = i;
                break;
            }
        }

        if (endIndex == -1) return "// Error parsing test body";

        return rawCode.Substring(startIndex + 1, endIndex - startIndex - 1).Trim();
    }

CORRECTIONS TO ALGORITHM 1:

  - NO LITERAL OR COMMENT AWARENESS. It is a bare character loop. A "{" inside a
    string literal, char literal, comment, or interpolated string ($"{x}")
    corrupts the depth count. REMOVE THAT CLAUSE FROM THE PSEUDOCODE.
  - IT DOES NOT LOCATE THE ENTRY-POINT SIGNATURE. It regex-matches
    Main\s*\(.*?\) and takes the first "{" after it.
  - NO MARKDOWN STRIPPING IN THIS PATH. Fence removal lives in a separate
    CleanCode (SolutionWriter.cs:229-233) applied to solver and benchmark code,
    but the test path calls ExtractMethodBodyRobust(data.Test) directly
    (SolutionWriter.cs:133) with no CleanCode first.

FAILURE MODES - no exceptions thrown, four silent sentinels:
    empty input          -> "// No test code found"
    no Main(             -> the raw input, unchanged
    no "{"               -> the raw input, unchanged
    unbalanced braces    -> "// Error parsing test body"
Each is emitted into generated source as a comment, producing a test method with
ZERO ASSERTIONS THAT COMPILES AND PASSES.

TWO UNDOCUMENTED POST-PROCESSING STEPS FOLLOW, both regex, both validity-relevant:

  InstrumentTestCode (SolutionWriter.cs:169-176) rewrites assertions:

    string pattern = @"if\s*\(\!([a-zA-Z0-9_]+)\.AreEqual\)\s*\{\s*throw new Exception\(\""(.*?)\""\);\s*\}";
    string replacement = "TestUtils.Check($1, \"$2\");";

  Any assertion not matching that exact shape is NOT INSTRUMENTED AND NEVER
  COUNTED - it silently vanishes from the pass/fail totals rather than failing.

  InjectNamespace (SolutionWriter.cs:222-227) regex-prefixes the entry-point call
  with the model namespace.

TWO STRUCTURAL NOTES:

  - SolutionExport.cs contains a SECOND, CLEANER GENERATOR using {NS} placeholder
    substitution. The shipped corpus was produced by SolutionWriter: the
    generated files carry its "TestUtils.Reset(); try { ... } catch" signature
    and CompareNetObjects import. DESCRIBE SolutionWriter, NOT SolutionExport.
  - NEITHER GENERATOR HAS A LIVE CALL SITE. CreateFiles, ExportSolutions and
    ReadSolutions are defined and never invoked. The generation stage cannot be

    public static List<int> MakeAPile(int n)
    {
        List<int> result = new List<int>();
        result.Add(n);
        for (int i = 1; i < n; i++)
        {
            if (n % 2 == 0) { n += 2; }
            else            { n += 2; }
            result.Add(n);
        }
        return result;
    }

The loop bound n is mutated inside the loop body, so i never overtakes it. The
loop terminates only when n overflows int to negative - roughly 1.07e9

detail. Every assertion fails because the returned list is astronomically wrong.

OBSERVATIONS FOR THE METHODOLOGY SECTION:
  - The solution prompt mandates "public class Solver", no namespace, and no
    Main. The corpus obeys this, which is why SolutionWriter can safely wrap
    each answer in a namespace block.
  - The benchmark prompt is a FOUR-MODEL artifact ("exactly 4 methods: GPT,
    Gemini, Claude, Grok"). The seven-model revision of this prompt was not
    found. The generated seven-model harnesses do contain all seven methods,
    so an updated prompt existed; it is simply not on disk.
  - NEITHER PROMPT SETS TEMPERATURE OR ANY DECODING PARAMETER. Q9 stands.
  - The prompts were stored per row, fully instantiated. That is good practice
    and should be stated in the paper as the provenance record.

*** ORIGIN OF THE INCORRECT N CLAIM (Q15) ***
The benchmark prompt INSTRUCTS the model to emit [Params(100, 1000, 10000)].
That instruction is where the manuscript's "N = 100, 1000, 10000" came from.
It is a specification of intent, not a record of what ran. Every one of the 79
generated harnesses in the current corpus carries [Params(10,100)], and the
BenchmarkDotNet artifacts confirm only N = 10 and N = 100 were ever executed.
The sizes were reduced at some point after generation - plausibly because the
larger inputs were too slow, which is consistent with the four build timeouts
in Q12. THE MANUSCRIPT MUST REPORT N = {10, 100}, the executed values.
